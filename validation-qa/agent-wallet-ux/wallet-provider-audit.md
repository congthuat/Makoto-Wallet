# Wallet picker audit and verification

The checkpoint modal rendered one generic Browser wallet button with an OKX icon. Its helper selected `window.okxwallet ?? window.ethereum`, so provider order determined the wallet used. The modal closed after every request because the store caught failures without returning their outcome. The inspected `validation-qa/ui-scroll/resume-baseline` copies had the same implementation. `brain-donor-reference/frontend/lib/wallet.ts` contained address/amount validation rather than a wallet picker; no donor signing, state, or UI code was imported.

`walletProviders.ts` now performs the native EIP-6963 event handshake and stores each provider object separately. Announcements are validated and deduplicated by UUID and provider reference. A copied UUID cannot replace a previously recorded provider. Compatible legacy injection is a fallback; a providers array is expanded into its individual providers. Announced providers require an explicit selection. Only pre-picker sessions with exactly one legacy provider retain the old compatibility fallback.

The chosen provider is committed after `eth_requestAccounts`, an Arc switch/add request, actual chain readback, and current-account readback succeed. A rejected, cancelled, unavailable-account, wrong-chain, or changed-account result cannot replace the current choice. Every existing `getProvider` consumer uses the selected object, including Send, Swap, CCTP, Tool Layer, SIWE and store subscriptions. Provider revisions refresh the existing account, chain and receipt-read effects without changing execution architecture. Disconnect/watch clears current session selection; existing watch-mode execution guards remain intact.

For reloads, the saved EIP-6963 preference contains rdns/name metadata, never a provider object or key. UUIDs are session-specific. A missing or ambiguous preferred wallet requires selection instead of falling back to another wallet. Wallet metadata is presentation information, not identity attestation. Icon data renders through `<img>` only. Invalid/broken announced icons fall back to local assets or a generic wallet icon.

Primary sources: [EIP-6963](https://eips.ethereum.org/EIPS/eip-6963), [EIP-1193](https://eips.ethereum.org/EIPS/eip-1193), [Rabby integration documentation](https://rabby.io/docs/integrating-rabby-wallet). Official assets downloaded locally from [MetaMask extension logo](https://github.com/MetaMask/metamask-extension/blob/main/app/images/logo/metamask-fox.svg) and [Rabby brand symbol](https://github.com/RabbyHub/logo/blob/master/symbol.svg); no image hotlinks or download links were added. The current OKX wordmark treatment was retained.

Verification: 21/21 provider tests, targeted type-check passed, targeted lint had zero errors and three inherited Fast Refresh warnings. The final isolated browser fixture run passed 30/30 cases: 24 no/one/multiple-wallet cases across 1440/390, EN/VI, dark/light, plus legacy connection, watch reload with an installed legacy provider, rejection, unavailable account, wrong-chain and cancellation followed by a late approval. Zero console errors, page errors, or forbidden wallet requests were recorded. Visual inspection confirmed desktop/modal and mobile/sheet layouts, truthful absent/detected states, individual icons and no horizontal overflow. The browser used real application/API rendering with wallet-only fixtures; no signature, approval or blockchain submission was requested.

Evidence: `wallet-browser-results.json`, `wallet-browser-qa.cjs` and `wallet-*.png` in this directory. App/API services were left running.
