# Architecture decisions — canonical Makotowallet.xyz

1. **Canonical ownership.** Makotowallet.xyz runtime is authoritative. Donor/reference code and documents provide candidate logic, not a second app. Current behavior wins over stale historical claims.
2. **Preserve product.** Retain the Surf-derived UI/UX and Vite/React plus Express stack. Do not restore Ledger Calm UI or copy a donor UI. Adapt Next/Wagmi modules at typed interfaces after audit.
3. **Noncustodial boundary.** Agent may READ, QUOTE, and PREPARE/WRITE bounded unsigned requests. External SDKs and providers are adapters, never Agent authority. No Agent-held signer. The user's wallet authorizes every transaction.
4. **Canonical action flow.** User Intent → Agent → Planner → Tool Layer → deterministic Policy/Risk → Simulation/Revalidation → Review → User Wallet Signature → Blockchain → Receipt → Re-read State → Continue/Done. Each arrow is a distinct evidence boundary. The current Send flow implements a subset; the chain is a target architecture, not a claim of current completeness.
5. **Typed tool boundaries.** READ returns observed state with provenance/freshness or unavailable/partial. QUOTE returns bounded provider estimates, expiry, and assumptions. PREPARE/WRITE returns bounded unsigned requests only. Provider-specific code stays behind Makoto interfaces.
6. **Deterministic safety.** Account, chain, asset/contract, recipient, amount, fee, allowance, slippage, simulation, expiry, and exact request are checked against fresh evidence. Missing evidence is not silently treated as a pass. Reuse current Send protections and stronger donor ideas where sound.
7. **Truthful lifecycle.** Preparation is not execution; wallet request is not submission; a hash is not confirmation. UNKNOWN is a first-class result, distinct from PENDING, FAILED, and CONFIRMED. Receipt and relevant state evidence are required for success. Provider failure cannot fabricate success.
8. **Current implementation first.** Prefer safe current code to replacement. Donor Send logic may be superseded by live Vite Send; donor shared safety, protocol, and indexer pieces still need independent evaluation.
9. **External data.** Surf DB unavailability is an external dependency, not an implied successful read or a blocker for local audit. Other third-party failures must surface as unavailable/partial.
10. **Phase governance.** Preserve the approved architecture phase order in `docs/ROADMAP.md`; track migration separately from historical completion. Do not begin Phase 13 until Phase 8–12 exit criteria are evidenced.
