# Public task security research

Research recorded before task authentication and multi-worker execution changes (2026-09-30). The selected packages are installed and exercised by the local regression suite. The research decisions and deployment limits remain the basis for the current implementation; see [task auth and ownership](TASK_AUTH_AND_OWNERSHIP.md) and [task execution claims](TASK_EXECUTION_CLAIMS.md) for verification evidence.

The middleware's default memory store is per-process; use shared backing or document an edge rate limiter for a multi-host deployment. No homemade IP bans. |

Use finite busy timeout and short `BEGIN IMMEDIATE` transactions for atomic claims and finalization. WAL allows concurrent readers and one writer on a supported local filesystem. This is same-file database coordination, not a network distributed lock. Reads happen outside write transactions. On crash, an expired claim may retry a read; only one result and notification may commit. |

## Design boundaries

- A SIWE session proves prior control of an address for this application. It gives the server no blockchain signing authority. Task automation remains read/notify or prepare-only.
- Challenge bytes, URI, domain, chain, nonce, issuance and expiration are set by the server. Nonces use cryptographic randomness, have a short lifetime, and are consumed atomically. The browser cannot supply authoritative ownership by adding `account` or `ownerAddress` to a request.
- Production must explicitly configure the public origin and a high-entropy session secret. Local development may use a documented localhost origin and a temporary secret, with sessions invalidated on restart. Never log challenge signatures or secrets.
- `owner_address` is immutable for new tasks and derived from the session. Existing unauthenticated rows cannot be silently assigned; quarantine them as legacy unclaimed and prevent their scheduled execution. Keep the data for review and documented recreation/claim policy.
- Browser `accountsChanged` changes the connected account, not the session owner. The UI must hide task data and request explicit re-verification on a mismatch. Switching transaction networks alone does not change authenticated identity.

## Deployment topology gate

The repository documents a local Node server and a local `backend/data/tasks.sqlite` (or `TASK_DB_PATH`). It does not specify a public host, number of instances, persistent volume, or shared session/claim datastore. The separate Drizzle/Postgres schema covers the waitlist through the Surf SDK; it is not evidence of a deployed shared task database. The intended topology must be supplied or documented before claiming public multi-host readiness.

| Topology | Task claim and session conclusion |
| --- | --- |
| A. One Node process with persistent local SQLite | Supported for local verification with the persistent session store. |
| B. Multiple processes on one host using the **same** SQLite file on a filesystem with working SQLite locks | The implemented atomic claim passed 100 two-process races on local temporary SQLite files; shared session and rate-limit counters were tested with independent connections. All processes must also share the session secret and auth database. |
| C. Multiple hosts with a network-mounted SQLite WAL file | Unsupported: [SQLite WAL requires processes on the same host](https://www.sqlite.org/wal.html). |
| D. Multiple hosts/containers with local or ephemeral files | Unsafe: each instance has a different task, claim, nonce, and session store. |
| E. Shared managed database/queue | Potentially suitable after selecting a real deployed service and verifying its transaction and session-store semantics; no provider is selected from guesswork. |

If the public target is C, D, or E, choose a genuinely shared datastore and adapt the small claim/session boundary after the target is known. A local SQLite lease does not make a multi-host deployment safe.
