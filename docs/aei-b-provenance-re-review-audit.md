# AEI-B provenance adversarial re-review — trust-source defect

**Review baseline:** `cad9fc3424cc53b3a5d343473e6b567ab25322e7` on `phase12h-planner-strategy-integration`, clean worktree and index. **Finding:** material trust-source defect; AEI-B remains IMPLEMENTED / PENDING REVIEW, **not READY_TO_CLOSE**. AEI-C and Phase 13 remain NOT STARTED.

## Reproduction before the fix

An arbitrary caller supplied a plain object containing its own request/session IDs, plan, legacy resolution, and purported structured user event for `SEND 10 EURC`. It computed the exact request, plan, event, field and evidence-set digests using the public deterministic rules. No trusted user-input boundary ran. `createPlannerParameterEvidence` returned `FIXED_USER_INPUT`, and `compilePlannerStrategy` returned `COMPILED`. The focused regression failed with actual status `COMPILED`. A recomputable digest proved consistency among caller-controlled values, not the origin of the user's choice. The prior positive test fixture had the same authority shape and was not isolated by a production-enforceable trust boundary.

Production import search found no caller of `compilePlannerStrategy`, `createPlannerStrategyBindingV2`, or `createPlannerParameterEvidence` outside the Planner/AEI modules and tests. There is also no production structured Planner confirmation capture. Lack of a current caller limits reachability today but does not make the exported public factory an authenticated source.

## Scoped fail-closed fix

Runtime commit `e66b2f8a8b82dfb34ca1cc300f50537da2951567` makes `createPlannerParameterEvidence` structural only. With no structured event it emits `UNVERIFIED` nonfixed records. With a caller-supplied event it returns `UNVERIFIED` failure; no public function in the present repository mints `FIXED_USER_INPUT`. A provider claim remains rejected by 11D's closed proposal schema. A handcrafted v2 fixed result, including matching digests, fails `validatePlannerParameterEvidence`; AEI-B rejects it as `INVALID_PARAMETER_EVIDENCE`. AEI-A v2 creation/validation also fails because it revalidates the same source. Legacy `RESOLVED` and v1 compiler inputs still fail the AEI-B gate. V1 AEI-A binding remains a structural historical data contract and cannot satisfy AEI-B's v2 input.

This deliberately removes the positive compile path used by the earlier test fixture. Fixture data and a plain event object cannot prove a real user action. A later approved trusted input boundary must establish origin authenticity before fixed Planner parameters can compile. This review does not implement that boundary, a confirmation UI, or AEI-C. **AEI-B is not ready to close** while its intended positive fixed-value path has no trusted source.

## Retest and limits

The fixed regression constructs a syntactically consistent forged event and recomputes all digests; fixed-origin minting and compilation both reject. Provider self-certification rejects. Six dynamic request classes (previous output percentage, all received, receipt, previous transaction, quote and runtime balance percentage) do not compile a proposed fixed fallback. Plain-language `Send 10 EURC` remains `UNVERIFIED`. Request/session/plan/goal/key/value, source, and digest substitution tests fail closed where evidence carries those fields; nonfixed evidence intentionally carries no authoritative value. A same-goal new plan ID invalidates old evidence. Malformed, symbol-keyed, accessor, proxy, prototype, duplicate and missing data reject without authority. `createdAt` remains structural and cannot overcome missing provenance.

AEI-B/provenance source audit found no fetch/RPC, wallet writer, signer, `writeContract`, `sendTransaction`, quote/preparation, receipt polling, retry/resubmission, persistence write, authoritative `Date.now`, or randomness. The separate Phase 11D wrapper may invoke its injected parameter provider to obtain an untrusted proposal; that call supplies no origin authority. Phase 9 policy, Phase 10F submission/recovery, Phase 12 state truth, and user-wallet final signing authority remain unchanged.

## Approved follow-up: AEI-B2 prerequisite

Documentation baseline `17a559e8dcb158c7827bf85db831a3086d1b03f1`, branch `phase12h-planner-strategy-integration`, clean worktree/index. Source inspection confirms the production architecture gap: `AgentMessage` (`frontend/hooks/useMakotoAgent.ts`) carries legacy Agent drafts/presentation; `AgentDraftContext` (`frontend/lib/agent/types.ts`) binds account/chain but no canonical Planner request/session/plan/goal identity. `ActionDraftCard.prepare` (`frontend/components/MakotoAgentPage.tsx`) selects or creates a handoff, stores it and navigates to wallet review. The handoff model (`frontend/lib/agent/actions/types.ts`) contains its own ID and action values, not exact Planner provenance. That Review click cannot authenticate an unrelated Planner parameter set.

The approved next work is **AEI-B2 — Trusted Planner Proposal Confirmation Boundary**, **DESIGN APPROVED / NEXT / NOT STARTED**. Its normative proposal model, runtime trust contract, production UI placement and implementation acceptance criteria are in [the provenance design](aei-parameter-resolution-provenance-design.md). It must carry retained request/session/plan/goal identity into a distinct visible Planner proposal review state, then create field evidence only after genuine explicit confirmation of the exact canonical set. Plain JSON/event shapes, model claims and matching digests remain insufficient. A runtime-only application capability must be distinct from the serializable evidence and cannot be reconstructed from it. This is an application trust boundary, not cryptographic protection against a compromised browser/XSS runtime.

Parameter confirmation is distinct from prepared transaction review and wallet signature. Dynamic numeric previews stay nonfixed; an explicit fixed replacement is new user input with new request/proposal provenance and fresh confirmation. AEI-B2 may enable the positive evidence-to-non-executable-skeleton path, but must stop before AEI-C materialization and leave full pipeline composition to AEI-F. AEI-B remains **IMPLEMENTED / PENDING REVIEW / BLOCKED** until implementation and renewed final review; AEI-C and Phase 13 are NOT STARTED. No runtime implementation or new test result is claimed here; prior verification counts above remain historical.
