## Existing action and tool capabilities

`PlannerIntent` supports SEND on Arc Testnet for a registered asset (USDC, EURC or cirBTC) to an explicit nonzero EVM recipient; SWAP on Arc Testnet only for the Xylo USDC↔EURC pair; BRIDGE only for Arc Testnet USDC → Base Sepolia USDC to an explicit recipient. These are semantic goal capabilities, not proof that every goal has an Agent execution handoff. `agent/canonicalIntegration.ts` accepts a separate `AgentIntent`, not `PlannerIntent`; its defaults and keyword/parser path must not be treated as a canonical conversion.

Phase 8 exposes read tools (`wallet.identity`, `wallet.state`, `network.verified`, `assets.balances`, `token.allowance`, `transaction.receipt`, `bridge.operation`, activity), matching `send/swap/bridge.quote`, and matching `send/swap/bridge.prepare`. Quotes require a wallet/account and verified chain; Send depends on balance and fee estimates, Swap on a Xylo quote and allowance, and Bridge on the direct CCTP forwarding route and fee/allowance evidence. Preparation reobtains a live quote, checks context and balance, and returns bounded unsigned steps with `executionEnabled: false`. It may introduce finite approval steps. None of these calls belongs inside a pure plan compiler. Provider SDK or arbitrary calldata/target data cannot enter through a Planner goal.

| Planner kind | Semantic-to-tool mapping justified by schema | Read/quote/prepare prerequisites | Agent execution status today |
| --- | --- | --- | --- |
| SEND | Arc registered asset + amount + recipient → `send.quote`/`send.prepare`, ACTION SEND. | Wallet account/chain, live balance, fee estimate, fresh quote/preparation; Phase 9 final review. | 10B has a separate user Review handoff when evidence passes. No Planner caller. |
| SWAP | Arc USDC↔EURC + input amount → `swap.quote`/`swap.prepare`, ACTION SWAP; finite APPROVE may be needed later. | Account/chain, chosen supported slippage at review boundary, Xylo quote, balance/allowance, simulation and final policy. | SWAP/finite Xylo approval can reach separate user Review. No Planner caller. |
| BRIDGE | Arc USDC → Base Sepolia, explicit recipient → direct `bridge.quote`/`bridge.prepare`, ACTION BRIDGE; finite approval may be needed. | Account/chain, source balance/allowance, CCTP fee and route, source-only status checks, final policy. | Quote/preparation exist; 10B has no canonical Agent wallet handoff for BRIDGE or bridge approval. Block Agent execution until that gap is separately resolved. |

Other Planner-to-tool routes are unsupported. A matching word in a UI action name does not add capability. `bridge.operation` is a separate status read and does not let a source receipt prove destination completion.

## Canonical binding and identity design

Introduce a **versioned `PlannerStrategyBinding`**, returned with a `StrategyCompilationResult`. The name follows existing `AgentTransactionBinding` and typed result conventions. It is a data-only, validated provenance record, not a policy decision or wallet capability. The compiler accepts only a validated v1 plan, a `RESOLVED` result whose plan ID matches, a complete one-to-one set of individually validated v1 intents keyed by goal ID and matching each goal kind, plus a trusted request/session context and an explicit deterministic identity/time input. It must reject malformed runtime values even when an upstream validator throws.

Proposed minimum binding fields: version; trusted request ID and Phase 12 session ID; plan ID and canonical digest of plan version/classification/goal IDs/kinds/dependencies; digest of goal-ID-keyed resolved intents; Strategy ID and digest of the exact Strategy skeleton; account/chain context reference when supplied by the connected-wallet boundary; and an exhaustive set of `{goalId, actionStepId, actionKind, dependsOnGoalIds}` entries. Canonical serialization sorts goals and dependency IDs, not the plan array. Digest comparison is a local integrity check against the reviewed inputs, not a signature, user consent, external evidence authentication, or proof of model semantics. Bind the original request identity outside the model; there is no current Planner request ID, so the eventual orchestrator must assign and retain one. Never use display labels, array positions, UI state, or implicit action-name matching as identity.

Derive bounded Strategy/step IDs deterministically from a domain-separated digest of validated request/session identity, canonical plan, resolved intents, and an explicit revision; use stable role suffixes for goal ACTION and technical WAIT/REVALIDATE steps. The exact encoding, collision check and input-size cap require contract tests. `createdAt` must come from an explicit validated host clock input, not model output or an ambient compiler read. The same complete input must produce byte-identical output. A new plan ID, changed graph/parameters/context or replan creates a new binding/revision, with prior attempts retained under 10F; it never silently mutates a submitted step.

**Two-stage contract:** the pure compiler emits a validated Strategy *skeleton*: ACTION steps with explicit confirmation and graph dependencies, no `preparedAction`, no quote/policy/receipt reference. It may add static WAIT_RECEIPT/REVALIDATE graph nodes only where the existing Strategy contracts can represent their ordering without claiming evidence. A separate, audited materialization boundary must later bind real Phase 8 quote/preparation references and maintain immutable historical step/attempt identity. Existing 10B/10C/10D need `preparedAction`; a skeleton alone is not executable. The current Strategy schema has no built-in content digest, revision or plan-origin field, so the binding plus materialization validation must supply that invariant before production wiring. Editing a prepared/submitted Strategy under the same ID without a checked revision is forbidden. Approval is a tool-derived technical step after allowance/preparation, not a fabricated Planner goal.

Identity chain required at every later boundary: trusted request/session → exact PlannerPlan digest and plan ID → goal ID/kind/validated intent digest → binding entry → Strategy ID plus content revision/digest → action step ID/action/dependencies → canonical quote and prepared-action fingerprint/index/account/chain → 10F attempt ID and submitted hash → 10C verified transaction/receipt → one permitted 12B/12D state edge. The v2 PLAN_READY state currently stores only plan ID; a future guarded PLAN_READY→PREPARED contract must verify this chain and the same session/plan, then use existing `bindAgentTransaction`. Until that guard and a trusted production caller exist, the edge remains denied and the UI stays unavailable. Historical restore is never fresh proof.

## Parameter ownership

`PLANNER-RESOLVED` means validated user-goal semantics, not a live observation. The current 11D resolver can apply unique capability defaults (Arc chain, opposite swap asset, direct CCTP route), but the compiler must revalidate the resulting intents and user meaning. `USER/WALLET-CONTEXT` is acquired independently from a connected wallet; it cannot be filled from Planner text. `POLICY-DERIVED` is a reviewed constraint/decision after evidence, never a compiler `ALLOW`.

| Action/field | Owner | Contract consequence |
| --- | --- | --- |
| SEND asset, decimal amount, recipient, Arc destination chain | PLANNER-RESOLVED | Validate registered asset, precision, positive amount, explicit nonzero recipient, Arc-only route. |
| SEND sender/account | USER/WALLET-CONTEXT | Bind to live connected account and verified chain before quote; no sender field in `PlannerIntent`. |
| SEND balance, fee, target calldata, expiry | TOOL/QUOTE-DERIVED; PREPARATION-DERIVED | Read/quote and prepare only; compiler emits none. |
| SWAP input/output assets, input decimal amount, Arc chain | PLANNER-RESOLVED | Only supported opposite USDC/EURC pair. Output amount is not resolved here. |
| SWAP account | USER/WALLET-CONTEXT | Must match quote, preparation, policy and later attempt. |
| SWAP slippage choice/review constraint | USER/WALLET-CONTEXT + POLICY-DERIVED | Existing tool accepts only fixed supported options; PlannerIntent has no slippage field. Do not silently copy `canonicalIntegration.ts`'s 0.5% default into compiler authority. Require explicit reviewed selection/approved default at orchestration boundary. |
| SWAP expected/minimum output, allowance, router, approval need | TOOL/QUOTE-DERIVED; PREPARATION-DERIVED | Fresh Xylo quote and bounded preparation; finite approval only if evidence requires it. |
| BRIDGE source/destination chains, USDC, decimal amount, recipient | PLANNER-RESOLVED | Only Arc → Base Sepolia direct CCTP route; recipient explicit. |
| BRIDGE sender/account | USER/WALLET-CONTEXT | Independently observed and bound. |
| BRIDGE mode/provider, fee, spender, burn calldata | TOOL/QUOTE-DERIVED; PREPARATION-DERIVED | Canonical direct CCTP tool decides route evidence. Model cannot select an arbitrary provider/target. |
| Every action's policy decision, simulation, freshness, final review | POLICY-DERIVED + TOOL/QUOTE-DERIVED | Phase 9 and existing review own these after preparation; none comes from the compiler. |
| Dynamic amount such as “all received EURC” | UNSUPPORTED | 11D asks for clarification. No output-value expression or receipt-to-amount binding exists in current PlannerIntent/Strategy. |

## Graph semantics and multi-step example

A plan edge `goal B dependsOn goal A` is an **order dependency**. Compile it by goal IDs into a path where A's ACTION must have 10C confirmed receipt evidence, and B requires fresh 10D re-read/requote/revalidation and a separate 10B/Phase 9 review. `WAIT_RECEIPT` and `REVALIDATE` nodes can make that order explicit; no array order, mere hash or persisted SUCCESS is sufficient. Independent ready branches still require one dependent write at a time. A **value dependency** is different: B's amount is a function of A's actual output. Neither `PlannerGoal.dependsOn` nor v1 `PlannerIntent.amount` (fixed decimal) expresses that function; 10D rereads/quotes an already fixed selected amount and does not derive a new amount from A's output. The compiler must reject or request clarification for that class, even if order is representable.

Example request: “Swap 100 USDC to EURC, then send the received EURC to 0x…”. 11B classifies STRATEGY; 11C can produce SWAP goal `g_swap` and SEND goal `g_send` with `dependsOn: [g_swap]`. 11D can resolve `g_swap` to Arc, USDC→EURC, amount `100`, subject to the actual address/text validation. It marks `g_send`'s dynamic “received EURC” amount as `DYNAMIC_AMOUNT`/`NEEDS_CLARIFICATION`, even if a provider supplies an invented decimal. Thus **today this request stops before canonical binding or Strategy creation**. If a user separately specifies a fixed SEND amount, a future compiler could emit the order-only skeleton, but quote/preparation, finite approval (if required), explicit Review, wallet signature, 10F record, 10C source receipt, new live balance/quote, 10D revalidation, and separate step-2 Review all remain separate calls; the missing compiler/materialization/orchestrator and 12B guard still block a production Agent chain today. A receipt or swap quote cannot be substituted for the amount of “all received.”

## Compiler result and fail-closed model

Propose a discriminated `StrategyCompilationResult`: `COMPILED` with the validated skeleton and binding, or `REJECTED` with typed, path/goal-ID-specific issues. No partial successful Strategy, silently dropped goal, inferred account, generated approval, or fallback to a different route. On replan, a prior result is stale and must be recompiled from the newly resolved plan. The compiler catches runtime inspection exceptions and returns a typed rejection; freeze/copy validated plain data before hashing or mapping.

| Rejection class | Required deterministic outcome |
| --- | --- |
| Invalid plan, unsupported version, duplicate goal ID, missing dependency, cycle, extra plan field | Propagate/map 11C issues to `INVALID_PLAN` / `UNSUPPORTED_VERSION` / `DUPLICATE_GOAL_ID` / `UNKNOWN_DEPENDENCY` / `DEPENDENCY_CYCLE` / `UNEXPECTED_FIELD`. |
| Missing/unresolved required field, ambiguous amount, dynamic output | `UNRESOLVED_PARAMETER`, `AMBIGUOUS_AMOUNT`, or `DYNAMIC_OUTPUT_UNSUPPORTED`; never invent decimal output. |
| Unsupported goal kind or no exact tool mapping | `UNSUPPORTED_GOAL_KIND` or `UNSUPPORTED_ACTION_MAPPING`; no name-based match. |
| Unsupported chain, asset/pair, route, invalid recipient | `UNSUPPORTED_CHAIN`, `UNSUPPORTED_ASSET`, `UNSUPPORTED_ROUTE`, `INVALID_RECIPIENT` using 11A and tool capability constraints. |
| Missing/mismatched wallet/account/session or incompatible dependency | `MISSING_WALLET_CONTEXT`, `CONTEXT_MISMATCH`, `CROSS_SESSION_REUSE`, or `INCOMPATIBLE_DEPENDENCY`. |
| Plan/result ID mismatch, missing/duplicate/extra intent, kind or digest mismatch | `PLAN_RESULT_MISMATCH` / `GOAL_BINDING_MISMATCH`; no positional pairing. |
| Getter, proxy, throwing object, prototype anomaly, hidden/symbol field, sparse array, cyclic/non-JSON value, unexpected field | `MALFORMED_RUNTIME` or `UNEXPECTED_FIELD`, even if an existing validator throws. |
| ID collision, stale plan/revision or changed bound digest | `IDENTITY_COLLISION`, `STALE_PLAN`, or `BINDING_MISMATCH`; no in-place repair after attempt creation. |

The compiler checks semantic/tool support, not balances or transaction safety. A valid `COMPILED` skeleton confers no wallet, policy, quote, preparation, submission, retry, receipt or execution authority. It must not call a quote provider, RPC, balance reader, `writeContract`, `sendTransaction`, signer, wallet unlock, or model; must not manufacture consent, receipt evidence, arbitrary calldata/target, or treat `ALLOW/WARN` as signing permission.

## Security and authority model

Goal/step substitution is stopped by the one-to-one binding plus Strategy digest and exact step ID. Parameter/dependency mutation changes the canonical plan/intent or Strategy digest and requires a new revision and user review. Account/chain/asset/recipient substitution is checked first against trusted session and validated intent, then quote/preparation/policy/attempt/receipt identities. Stale plans and cross-session replay require a new trusted request/session binding and re-resolution; a copied binding is inert data. Model-supplied or UI-supplied IDs and labels alone are insufficient. Runtime objects with getters, prototypes, proxies, hidden/symbol fields and arbitrary transaction targets fail at a closed input boundary before any tool acquisition. An attacker-controlled digest is not proof; the trusted orchestrator must recompute it from retained canonical inputs.

Phase 9 keeps transaction policy authority with precedence **BLOCK > REQUOTE > REVALIDATE > REQUIRE_REVIEW > WARN > ALLOW**. A non-stopping decision still requires explicit user review. Phase 10 keeps one-step execution, receipt and continuation contracts; 10F alone interprets attempt/retry and double-submission safety. Phase 12 keeps truthful, one-edge state transitions and historical-only restoration. The connected user wallet remains final signing authority. The compiler may describe intent but never signs, submits, retries, resubmits, polls, claims confirmation, or advances AgentState.

## Proposed production orchestration boundary (not implemented)

A dedicated application-domain orchestrator, outside a React component and outside the LLM/provider adapter, would hold trusted request/session identity and sequence: user request → 11B/11C → 11D → canonical compiler/binding → one Strategy skeleton → Phase 8 account/network reads, quote and bounded preparation for one eligible action → Phase 9 and 10B review gate → explicit user Review and wallet signature → 10F attempt record → one 10C read/verification → guarded 12B/12D state edge → 10D fresh evidence → 10E eligibility → next separate review. It must keep preparation/attempt artifacts tied to the exact binding revision and reject any changed plan, account, chain, output or prior attempt. A React page can render this state and invoke explicit user actions; it is not the authority that synthesizes evidence. The LLM remains an untrusted proposal source. Direct CCTP Agent execution and dynamic output-derived amounts remain blocked until their own contracts exist. No restored state can auto-resume this pipeline.

AEI-B1 inserts the proposal-only production prefix before compiler/binding: Agent request → retained request/session → exact validated PlannerPlan and goal-ID-keyed semantic parameter candidates → immutable canonical proposal in distinct Agent UI state. B1 ends without user confirmation or Strategy compilation. AEI-B2 then displays that exact proposal and captures application-authenticated parameter confirmation → field evidence. Confirmation means the displayed values express user intent; prepared transaction review and wallet signature remain later, separate boundaries. AEI-F will compose this source with AEI-C/D/E and the existing execution contracts; B1 and B2 do not bring their work forward.

## Phase placement recommendation and acceptance gate

**The audit recommended a separate Agent Execution Integration milestone before Phase 13 rather than retroactively reopening Phase 12 as 12H.** The approved ROADMAP now inserts **Integration Milestone — Agent Execution Integration** between the closed Phase 12 and Phase 13, without renumbering Phases 13–17. This work spans Phase 11 provenance, Phase 10 Strategy revision and execution materialization, Phase 8/9 evidence, Phase 12 schema/guard/UI, and production orchestration; it exceeds an AgentState-only subphase. The `12H` worktree and document title remain historical audit labels. Phase 13 remains untouched and NOT STARTED.

Before any end-to-end Agent transaction claim, acceptance requires an immutable, tested plan→goal→step binding; a versioned Strategy materialization rule; fresh account/chain/quote/preparation/policy and explicit wallet Review; 10F attempt safety; 10C receipt plus 10D/10E continuation; a newly guarded Phase 12 PLAN_READY→PREPARED path and truthful production caller/presentation; and adversarial verification. Current blockers are missing canonical binding/compiler/orchestrator, missing Strategy content-revision binding, denied Phase 12 edge, no Direct CCTP Agent handoff, and no dynamic output-value contract. Pure 12E still does not authenticate the external acquisition origin of a supplied receipt observation; runtime host clock accuracy remains a dependency. None of these limitations grants execution authority.
