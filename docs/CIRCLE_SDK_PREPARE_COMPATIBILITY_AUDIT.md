## Prepared request identity, simulation, and wallet authority

**Bridge Kit.** `BridgeKit.bridge()` resolves the provider and calls `provider.bridge()` in the same operation (`B/index.mjs`, `BridgeKit.bridge`, around 14334-14363). `estimate()` is a separate pricing call, not a held wallet request (`B/index.mjs` around 14499-14526). `B/index.d.ts`, `BridgeParams.quote` around 12038-12078 states that CCTPx may transparently reprice a stale or mismatched quote, while ordinary CCTP v2 USDC ignores a supplied quote. Steps, events, callbacks, and the adapter's `onBeforeAuthorize` hook provide observability or an in-flow veto; they do not supply Makoto's separate approval receipt, re-quote, review, and burn handoffs. **Verdict: `NOT_COMPATIBLE_WITH_REVIEW_BOUNDARY` for `bridge()`**. This preserves the earlier App Kit finding.

**Viem legacy root.** `A/index.d.ts` defines `EvmPreparedChainRequest` with `estimate`, `execute`, and optional `getCallData`; it has no `simulate` on that prepared interface. `EvmExecuteOverrides` includes `from` and `value`, and `A/index.mjs` spreads overrides into `sendTransaction` after prepared fields (around 25598-25609, 25974-25989). Calling `execute({ value: ... })` can change the reviewed value. **Verdict: `PARTIALLY_COMPATIBLE`; do not use this root path for the proposed request-identity boundary.**

**Viem `/next`.** `A/next.d.ts`, `RawTransaction`, `PreparedEVMTransaction`, and `PreparePrimitive` (around 6242-6251 and 10943-10965) define `prepare(input, operation)` → `EVMPrepareResult`; `result.single()` returns `input`, `built: { to, from, data, value }`, `estimate()`, `simulate()`, and `execute(overrides?)`. `chain` and address are bound in the operation context. `A/next.mjs`, `createPrepare` (around 25712-25759) captures `built`; the prepared object's `execute` passes that same raw object to `createExecute`, which builds the payload from `to/data/value` and the captured chain, checks the sender, authorizes, and calls the viem WalletClient (`createExecute`, around 24703-24804). It does not recalculate a quote or re-encode calldata in `execute`. `GasOverrides` allows only `gas`, `gasPrice` or EIP-1559 fees, and `nonce` (`A/next.d.ts` around 6270-6288). The pre-authorization callback receives a cloned payload and can approve/reject, not rewrite it (`A/next.mjs` around 11141-11184).

This is **structural identity for the material EVM call**, not an SDK-supplied cryptographic request ID and not proof that an external wallet cannot alter its final transaction. TypeScript `readonly` does not freeze `built` at runtime. Makoto must compute its own canonical fingerprint; reread live `eth_accounts`/`eth_chainId`; compare `to/from/data/value`, chain, account, recipient, asset, spender, amount, fee cap, quote and expiry; then execute the **freshly compared prepared object** with explicitly reviewed gas/fee/nonce bounds. If the EIP-1193 wallet request or post-submission transaction differs, stop or classify UNKNOWN. The provider factory caches its first resolved account promise (`A/next.mjs` around 27083-27139), making Makoto's fresh account read essential.

`PreparedEVMTransaction.simulate()` is **`SAFE_PRE_SIGN_SIMULATION`**: `A/next.mjs`, `createSimulate` around 24348-24402 uses `PublicClient.call` (`eth_call`) with prepared `from/to/data/value`, returns success and return data or a normalized soft failure, and performs no signature or state-changing send. RPC errors also produce failure, so Makoto must distinguish unavailable evidence from a proven revert. `estimate()` is separate and read-only. The adapter's `createViemAdapterFromProvider({ provider })` accepts an EIP-1193 provider, uses a viem custom transport and a WalletClient, and does not require a private key (`A/next.mjs` around 27032-27139). OKX/MetaMask-style connected wallets can be the sole signer; the private-key quickstart is an example, not a requirement.

`/next` also supplies a **legacy compatibility shim**. Provider calls to `adapter.prepareAction(...)` become new `action.prepare(...)`; a single EVM action is enriched with `type: 'evm'` and `getCallData(): {to,data,value}` (`A/next.mjs`, `adaptWriteAction` around 23684-23774 and `enrichEVMWriteRequest` around 21377-21387). Its `execute()` invokes that same captured prepared transaction and returns the tx ID before receipt waiting. The getter omits `from` and chain; Makoto must bind them separately. Multi-write/no-op outputs must fail closed for the single-write review path. The shim's inner execution validates gas/fee/nonce overrides only. **`/next` verdict: `COMPATIBLE_BEHIND_MAKOTO_WRAPPER`.**

**Immediate revalidation model:** prepare A → inspect and review A → immediately prepare B from fresh state and fee evidence → compare canonical material fields and quote constraints → if equal execute B's prepared `execute()` once → independently verify the wallet transaction and receipt. The SDK does not provide a fingerprint; Makoto's fingerprint and freeze must include `chainId`, account/from, `to`, calldata, `value`, gas limit/price bounds, approval spender/amount, burn token/amount/domain/mint recipient/hook/maxFee/finality, quote identity/expiry, and expected destination/receive floor. A change invalidates review. Executing A after a fresh B comparison would weaken freshness.

The adapter README sample that calls `estimate/simulate/execute` directly on the overall prepare result disagrees with the exported types: those methods are on `result.single()` or `transactions[i]`; the aggregate result has `estimateTotal()` and sequential `execute()` (`A/next.d.ts`, `PrepareResult` around 4511-4545). Types/source win.

**Declaration packaging risk:** the published `/next` declaration bundle has absolute CI build path imports for `zod` and `PrivateKeyAccount` (`A/next.d.mts` lines 22-23). An isolated consumer type check of the provider plus `/next` adapter passed with `skipLibCheck`, but a strict check without it failed on those publication paths (and Solana dependency Node types). This is not evidence of a runtime adapter/provider mismatch; it is a concrete type-check issue to resolve or isolate before implementation. The compatibility conclusions here come from the runtime source and exported API shapes, not from assuming a clean strict package compile.

## CCTP v2: Arc USDC

`CCTPV2BridgingProvider` exports `estimate`, `getMaxFee`, `supportsRoute`, independently prepared `approve(source, amount)`, `burn(params)`, `mint(...)`, `fetchAttestation`, `fetchRelayerMint`, and `reAttest`; its `bridge()` owns the entire sequence and is excluded (`C/index.d.ts`, `CCTPV2BridgingProvider` around 7737-8292). It supports **USDC only**: `supportsRoute(..., token: 'USDC')` and the implementation reject other tokens (`C/index.d.ts` around 8224; `C/index.mjs` around 16474-16492). The 1.14.0 chain definitions and `supportsRoute` make **Arc Testnet (domain 26) → Base Sepolia (domain 6), with forwarding** route-eligible; both are testnet CCTP v2 chains and Base Sepolia permits forwarding destination. This is metadata/source evidence, not a live quote or transfer test.

| CCTP step | Official primitive and exact boundary | Makoto treatment |
| --- | --- | --- |
| Fee / quote | `estimate()` and `getMaxFee()` read current network fees. `getMaxFee` uses transfer speed and forwarding, defaults to FAST, and can add a 10% fast-fee buffer; `config.maxFee` pins an explicit cap (`C/index.mjs`, `getMaxFee` around 16531-16581). There is no stable quote/request ID on ordinary `burn()`. | Keep fresh Circle fee read, 45-second expiry and exact-receive policy until fee/amount semantics are reconciled. Pass explicit speed and reviewed fee cap. |
| Allowance | Adapter `usdc.allowance` / `token.allowance` is a read action; Makoto's existing `readAllowance` also reads it before and after approval. | `KEEP_MAKOTO` for verified state and thresholds. |
| Approval | `provider.approve(source, amount)` returns `PreparedChainRequest`; source prepares `usdc.increaseAllowance` for the chain's TokenMessenger and **amount is an increment**, not an exact final allowance (`C/index.mjs` around 16181-16202). With `/next`, a single request exposes `getCallData` and executes that captured request. | Separate pre-sign review is possible, but this is **not** a drop-in replacement for Makoto's finite `approve(spender, totalDebit)`. Keep exact finite approval unless a wrapper proves current+increment is within the reviewed cap. Never infer unlimited approval. |
| Burn | `provider.burn(params)` separately returns `PreparedChainRequest`, selecting `cctp.v2.depositForBurn` or `depositForBurnWithHook` (or supported custom-burn variant) after resolving fee, recipient, contract and hook (`C/index.mjs` around 16606-16674). With `/next`, single EVM `getCallData()` reveals exact `to/data/value`; the captured request executes unchanged under the adapter. | `WRAP_OFFICIAL`: check selected target and decoded calldata against policy, simulate the same raw call, review, refresh fees and prepare B, compare, then execute B only. |
| Source and forwarding status | `fetchAttestation` and `fetchRelayerMint` supply Circle message/attestation/relayer state. A forwarder-only provider path can regard IRIS `CONFIRMED` as completion with `forwardTxHash` (`C/index.d.ts` around 6850-6860; `C/index.mjs` around 12495-12498). | Require Makoto's independent source transaction/receipt matching and destination RPC receipt plus matching USDC Transfer. IRIS status or callback alone is not destination confirmation. |

**Separate flow verdict: YES behind Makoto wrapper**, for a single EVM approval request and a later single EVM burn request: allowance → optional separately reviewed finite approval → source receipt → allowance reread → fresh fee/quote → prepared burn → policy/simulation/review → immediate prepare/compare → user-wallet execute → source receipt → Circle attestation/forward hash → destination receipt and recipient state evidence. `provider.bridge()` and its retry orchestration are not used. The official low-level provider makes approval and burn independently preparable; Makoto owns every pause and continuation. The provider's `burn` amount is the **amount burned** and it computes a max fee from that amount; Makoto currently burns `desired receive + max fee` and has a separate expected-receive floor. Replacing Makoto's amount/fee math without reconciliation could change the amount received. The standard forwarding path can depend on Circle's relayer; a returned forward hash is still not a destination receipt.

The direct provider implementation consumes `config.maxFee` in **minor units** (`C/index.mjs` around 16537-16542), although generic `BridgeConfig` declaration text discusses human-readable units (`C/index.d.mts` around 6163-6168); the source wins. The high-level provider may batch approval and burn unless `batchTransactions: false`; the independently called `approve` and `burn` avoid that hidden batch. Source receipt status is available through adapter `waitForTransaction`; `fetchAttestation` returns Circle message/nonce/attestation/status, while `fetchRelayerMint` accepts IRIS `CONFIRMED` or `COMPLETE` with a forward hash. `CONFIRMED` may still await destination finality, so Makoto's independent Base receipt/Transfer check remains required (`C/index.d.mts` around 6762-6860; `C/index.mjs` around 12495-12498, 16300-16360).

The official `AttestationMessage` type includes raw `message`, `eventNonce`, attestation and decoded fields but **no explicit message-hash field**; [Circle documents the message hash as `keccak256` of emitted message bytes](https://developers.circle.com/api-reference/stablecoins/common/get-attestation). Makoto must correlate the selected raw message with the source receipt and reviewed transfer. Current `backend/routes/cctp.js` reads `payload.messages[0]`; before extending routes, message selection should be checked against source event/domain/recipient/amount rather than relying on array order. This audit did not change that route.

## CCTPx: EURC, cirBTC, and wETH

`CCTPXBridgingProvider` exports `estimate`, `bridge`, `retry`, route/registry helpers, signed fee-quote helpers (`fetchCCTPXFeeQuote`, `isQuoteFresh`), `fetchCCTPXAllowances`, `fetchCCTPXAttestation`, and `reAttestCCTPXMessage` (`X/index.d.mts` public exports around 8445-8446). **It exports no independent `prepareApproval`, `prepareTransfer`, `simulate`, or execute-prepared method.** Internal `prepareApprove` and `prepareTransfer` call adapter actions, but `bridge()` then executes them internally, sequentially or through an EIP-5792 approval+transfer batch (`X/index.mjs` around 10004-10037, 10275-10329, 11367-11440, 11793-11936). `batchTransactions: false` avoids batching, yet leaves the entire sequence inside `bridge()` and gives Makoto no stop after approval. **`provider.bridge()` verdict: `NOT_COMPATIBLE_WITH_REVIEW_BOUNDARY`; Makoto asset path: `BLOCKED_PENDING_PROVIDER_API`.**

The internal bridge-token approval is finite: the spender is the source token's TokenManager from the IRIS registry and the amount is the exact transfer amount. If an ERC-20 fee token is selected, a second finite approval uses the source CCTS service address and quoted `feeTotalAmount`; the normal provider requests native-fee payment, attached to the transfer as `msg.value`. There is no max-uint approval default (`X/index.mjs` around 10004-10037, 11808-11814, 11951-11962). These details are visible in source but **not exposed as separately reviewable public prepared requests**. The package does not expose a suitable ERC-20 allowance read/skip step; its `fetchCCTPXAllowances` is an off-chain **fast-burn budget** probe, not wallet token allowance.

`estimate().quote` carries signed quote bytes, fee token, total and itemized fees, nonce, `expiresAt`, expiry mode and optional `expiresAtBlock`; it does not expose a gas estimate or explicit minimum receive. `isQuoteFresh` checks wall-clock `expiresAt`; for `BLOCK_NUMBER` expiry, this timestamp is advisory and the on-chain `expiresAtBlock` is authoritative (`X/index.d.mts` around 299-367; `X/index.mjs` around 9860-9902, 13787-13849). `bridge()` can transparently refetch a stale quote, change signed quote/fee/calldata, and downgrade FAST to SLOW when its off-chain fast-burn budget is insufficient (`X/index.mjs` around 12089-12149, 13769-13795). Quote reuse does not prove route/amount/recipient identity to Makoto; contract validation may merely revert a mismatch. The approval spender/amount and transfer fee/value can therefore differ between review of an estimate and the wallet prompt. Events and returned steps are **OBSERVABILITY ONLY**.

The versioned package pins canonical token IDs for **EURC, cirBTC, wETH**. The production and sandbox IRIS registry entries checked on 2026-09-30 show these **route-eligible** Arc pairs, in both directions (`X/index.mjs`, token IDs around 124-169 and `supportsRoute` around 13090-13171):

| Asset | Arc mainnet CCTPx destinations | Arc Testnet CCTPx destinations |
| --- | --- | --- |
| EURC | Ethereum, Base | Ethereum Sepolia, Avalanche Fuji, Base Sepolia |
| cirBTC | Ethereum | Ethereum Sepolia |
| wETH | Ethereum | Ethereum Sepolia |

These are registry/deployment routes, not evidence of a successful live fee quote or transfer. The mainnet EURC canonical CCTPx registry entry does **not** include Avalanche, even though [EURC exists there](https://developers.circle.com/stablecoins/eurc-contract-addresses). CCTPx requires its relayer/forwarder path; `supportsRoute` gates EVM, same network, distinct CCTS domains and registry deployments, while `estimate/bridge` reject disabling the destination forwarder. Arc and Arc Testnet both have CCTS service deployments. The package type comment at `X/index.d.mts` around 2628 says EURC still uses CCTP v2; that is stale against the current `B/index.mjs` provider dispatch (USDC to CCTP v2, other supported tokens to CCTPx), CCTPx's canonical EURC IDs, and the live registry. Actual source/registry win.

CCTPx source steps contain a source hash and the provider checks mined source receipt status; `fetchCCTPXAttestation` supplies message/attestation/status/event nonce. IRIS forwarding may report `CONFIRMED` with a `forwardTxHash` before final `COMPLETE`; the provider does not fetch an independent destination RPC receipt or recipient token state (`X/index.mjs` around 10862-10981, 11108-11166). Makoto would have to verify those separately if a public prepared-write API became available. No user-wallet write path is recommended for EURC or cirBTC now.

The exported CCTPx `CCTPXMessage` similarly has raw message bytes, event nonce and attestation but no explicit message-hash property (`X/index.d.mts` around 7240-7270). Any message hash or destination proof would require an independently verified derivation and receipt correlation.

## POST-INTEGRATION VERIFIED — 2026-10-01

This dated addendum updates the runtime status after integration. It preserves the audit evidence and conclusions above as the pre-integration checkpoint; statements above that implementation had not started describe that earlier checkpoint only.

Pinned `@circle-fin/adapter-viem-v2@1.18.0` and `@circle-fin/provider-cctp-v2@1.14.0` are installed. Runtime metadata confirms Arc Testnet (5042002/domain 26) → Base Sepolia (84532/domain 6), USDC only, and the Circle Testnet custom bridge `0xC5567a5E3370d4DBfB0540025078e283e36A363d`. The provider's `supportsRoute` confirms this USDC forwarding route. The current route's `provider.burn()` prepares `bridgeWithPreapprovalAndHook` against the custom bridge; the actual prepared calldata is decoded and checked, simulated, fingerprinted and captured through `/next`. Makoto continues to execute only the one reviewed `/next` transaction through the connected EIP-1193 wallet. No `kit.bridge()` execution is used.

The observed route-specific burn differs from the standard TokenMessenger deposit shape summarized in the pre-integration source audit. The custom bridge calls TokenMessenger internally: the emitted CCTP message sender is validated against TokenMessenger, and the message body's `messageSender` is validated against the custom bridge. This is based on installed route metadata and generated prepared-call fields, not a change to Circle's generic direct-deposit API. Approval remains a separately prepared exact finite ERC-20 approval to the route's verified custom-bridge spender; the provider's incrementing `approve` method remains unused.

The implementation now has the integration and test evidence in [CIRCLE_CCTP_V2_INTEGRATION.md](CIRCLE_CCTP_V2_INTEGRATION.md), [cctpAdapter.ts](../frontend/src/protocols/circle/cctpAdapter.ts), and `validation-qa/cctp-official-circle/report.md`. EURC/cirBTC CCTPx write execution remains blocked, Universal Bridge remains partial/disabled, and a real wallet signature or transfer remains a separate user-authorized test.
