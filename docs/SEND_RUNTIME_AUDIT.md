## Implementation choice

The current app already supplied an injected EIP-1193 provider, token list, backend explorer reads, a Vite UI, deterministic brain review, and one-time Agent handoff. Donor `transactionOrchestrator.ts`, `transactionReview.ts`, `transactionReceipt.ts`, `arcFees.ts`, `assets.ts`, and `walletSafety.ts` were inspected. Directly importing the donor would require Next.js/Wagmi and donor provider assumptions. The Vite-compatible `lib/sendExecution.ts` implements the reusable exact-request, fee-reserve, review and receipt ideas against the existing provider with a smaller runtime change. No donor UI was copied.

## Validation and limits

- Focused Send tests cover decimals/calldata/MAX, invalid and contract recipients, affordability, account/chain/token/amount/recipient/request/expiry invalidation, wallet rejection/hash, duplicate guard, and receipt success/failure/pending/unknown. Existing brain tests cover Agent handoff, prepare-only boundary and review/Policy behavior.
- Browser QA used a local injected EIP-1193 mock that never signed or broadcast a transaction. Its fake hash/receipt and local Activity record were isolated to the QA browser session. This proves UI wiring and state transitions, not real wallet interoperability or Arc inclusion.
- Connected gas bounds use 1.2 times `eth_estimateGas` and at least 20 Gwei or twice the observed `eth_gasPrice`; the upper fee shown in review is included unchanged in the wallet request. RPC fee changes between review and confirmation invalidate the snapshot. Actual wallet fee is ultimately shown by the user's wallet.
- Connected review shows the full entered token precision, including eight cirBTC decimals. It rounds the maximum gas fee upward into six-decimal USDC units and derives USDC total from integer units, so the displayed maximum does not understate the reserved amount.
- A real manual test should use a small supported asset transfer to a user-controlled EOA on Arc Testnet, verify the wallet request's chain/token/recipient/amount/max fee, and then inspect the hash, matching receipt, updated balances, and deduplicated Activity. The user must initiate and approve that transaction.
